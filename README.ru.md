# git-gone

[![CI](https://github.com/rasuvaeff/git-gone/actions/workflows/ci.yml/badge.svg)](https://github.com/rasuvaeff/git-gone/actions/workflows/ci.yml)
[![License: MIT OR Apache-2.0](https://img.shields.io/badge/license-MIT%20OR%20Apache--2.0-blue.svg)](./LICENSE-MIT)

**Удаляет локальные Git-ветки, чей remote удалён — в одном репозитории или сразу
по всему дереву вложенных репозиториев.**

Маленькая быстрая CLI на Rust без рантайма. Находит локальные ветки, которые
отслеживают remote-ref, которого больше нет (`[gone]`), и удаляет их. Текущая
(выбранная) ветка никогда не удаляется.

## Зачем

`git fetch --prune` подрезает `origin/...` tracking-ссылки, но **оставляет
локальные ветки**. Со временем накапливаются десятки мёртвых веток. `git-gone`
заканчивает начатое — и, уникально, умеет сделать это для **целого монорепо**
из вложенных репозиториев одной командой.

### Киллер-фича: multi-repo режим

Если вы работаете в workspace, где много маленьких git-репозиториев лежат
рядом (vendor-монорепо, папка `~/src` с клонами, дерево микросервисов), чистить
gone-ветки по одному репо утомительно:

```bash
$ git gone -r --list
Scanning 58 repositories...

clickhouse-toolkit:
  chore/gitattributes-export-ignore
  chore/package-quality-alignment

domain-monitor:
  chore/package-quality-alignment
  mutation/msi-100

yii3-mcp:
  feat/interceptors
  feature/v1.2-core

29 gone branch(es) across 17 repositories (of 58 scanned).
```

Одна команда — все вложенные репо. Ни один другой `git-gone` так не умеет.

### Локаль-независимость

Многие скрипты ищут gone-ветки по строке `[gone]` в `git branch -vv`. Git
**переводит** эту строку: на русской локали это `[отсутствует]`, на французской
`[disparue]` — grep молча ничего не находит.

`git-gone` резолвит каждый upstream через plumbing-команды Git (один пакетный
`git cat-file --batch-check` на репозиторий) и считает неразрешимый ref
признаком gone. Работает одинаково на любой локали.

## Установка

Требуется `git` 2.7 или новее на `PATH` (инструмент управляет вашим собственным `git`).

### Одной командой (Linux и macOS) — без Rust toolchain

```bash
curl -fsSL https://raw.githubusercontent.com/rasuvaeff/git-gone/master/scripts/install.sh | sh
```

Переопределить место установки через `INSTALL_DIR=…` (по умолчанию
`/usr/local/bin`; откат на `~/.local/bin` при отсутствии прав и `sudo` работает
только для директории по умолчанию — явно заданный `INSTALL_DIR` при
невозможности записи даёт ошибку, а не установку в другое место). Зафиксировать
и installer, и release asset можно, получив installer из тега релиза:

```bash
VERSION=v0.1.0
curl -fsSL "https://raw.githubusercontent.com/rasuvaeff/git-gone/${VERSION}/scripts/install.sh" | VERSION="$VERSION" sh
```

Загрузка проверяется по `.sha256`, опубликованному вместе с релизом; при
несовпадении установка прерывается.

### Windows (PowerShell)

```powershell
irm https://raw.githubusercontent.com/rasuvaeff/git-gone/master/scripts/install.ps1 | iex
```

Ставит в `%LOCALAPPDATA%\Programs\git-gone` (переопределяется
`$env:INSTALL_DIR`) и добавляет в пользовательский `PATH`. Зафиксировать и
installer, и release asset можно так:

```powershell
$env:VERSION = "v0.1.0"
irm "https://raw.githubusercontent.com/rasuvaeff/git-gone/$env:VERSION/scripts/install.ps1" | iex
```

### Cargo

```bash
cargo install git-gone-multi
```

Crate называется `git-gone-multi` (имя `git-gone` на crates.io занято чужим
проектом), но **устанавливаемый бинарь — `git-gone`**, алиас `git gone`
работает как обычно. Если другой `git-gone` уже стоит через cargo, бинари
конфликтуют — добавьте `--force` для замены.

Или напрямую из репозитория:

```bash
cargo install --git https://github.com/rasuvaeff/git-gone
```

### Ручное скачивание

Пребилд-бинари для `x86_64-unknown-linux-gnu`, `aarch64-apple-darwin`,
`x86_64-apple-darwin`, `x86_64-pc-windows-msvc` — на странице
[Releases](https://github.com/rasuvaeff/git-gone/releases). Linux-сборка
слинкована с системным glibc; для других Linux-таргетов (aarch64, musl) —
установка из исходников.

### Запуск как `git gone`

Git автоматически находит `git-gone` на `PATH` — после установки можно писать
и `git gone`, и `git-gone`.

## Использование

### Один репозиторий (по умолчанию)

```
$ git gone
Fetching and pruning remote-tracking refs...
Gone branches (2):
  feature-x (2 unmerged commits)
  refactor/auth
Delete these 2 branches? (y/N) y
Deleted branch: feature-x (was 4f2a1c9)
Deleted branch: refactor/auth (was 91b0e77)
Recover a deleted branch with: git branch <name> <sha>
Done.
```

`(N unmerged commits)` помечает коммиты, недостижимые ни из одного другого
ref — то, что форсированное удаление реально потеряет (кроме reflog). У
влитой ветки суффикса нет.

### Multi-repo (`--recursive`)

```
$ git gone -r --yes
Deleted clickhouse-toolkit/chore/gitattributes-export-ignore (was 4f2a1c9)
Deleted clickhouse-toolkit/chore/package-quality-alignment (was 0d19ab3)
Deleted domain-monitor/mutation/msi-100 (was 77c5e21)
Done.
```

Другое дерево можно сканировать без смены текущего каталога:

```bash
git gone -r --root ~/src --dry-run
```

### Флаги

| Флаг | Кратко | Действие |
|---|---|---|
| `--recursive` | `-r` | Сканировать поддиректории и обработать **все** вложенные git-репозитории |
| `--root PATH` | | Сканировать это дерево каталогов с `-r` (по умолчанию: текущий каталог) |
| `--depth N` | | Макс. глубина сканирования с `-r` (`0` = только корень сканирования, `1` = прямые поддиректории; по умолчанию без лимита). Сам корень осматривается всегда |
| `--exclude a,b,c` | | Имена каталогов через запятую для пропуска (заменяет `git config gone.exclude` и умолчание `target,vendor,node_modules,.cache,build,dist`) |
| `--jobs N` | `-j` | Сколько репозиториев фетчить параллельно при `-r` (по умолчанию: число CPU, максимум 8) |
| `--safe` | | Использовать `git branch -d`: удалять только ветки, которые Git считает смерженными (по умолчанию форсированный `-D`) |
| `--protect a,b` | | Паттерны имён веток (wildcard `*`), которые никогда не являются кандидатами на удаление; добавляется к `git config gone.protect` |
| `--json` | | JSON-отчёт (подразумевает режим отчёта: без удаления; конфликтует с `--yes`) |
| `--include-reasons` | | Добавить upstream и число непересекающихся коммитов в вывод `--json` |
| `--allow-external-git-dir` | | С `-r` разрешить Git-метаданные linked worktree вне `--root` (только для доверенных деревьев) |
| `--list` | `-l` | Напечатать gone-ветки, ничего не удалять |
| `--dry-run` | `-n` | Показать, что было бы удалено, без удаления |
| `--yes` | `-y` | Пропустить подтверждение (для скриптов/CI) |
| `--no-fetch` | | Пропустить начальный `git fetch --prune` |

`--depth`, `--exclude`, `--jobs`, `--root` и `--allow-external-git-dir` имеют
смысл только с `-r` и без него отвергаются. `--include-reasons` требует `--json`.

### Конфигурация (`git config`)

| Ключ | Значение |
|---|---|
| `gone.protect` | Паттерны имён веток (wildcard `*`, многозначный ключ или через запятую), которые никогда не кандидаты на удаление. Действуют repo-local, global и system уровни; `--protect` добавляется к ним. Пропуск объявляется: `Protected branches skipped: develop` |
| `gone.exclude` | Имена каталогов, пропускаемых сканом `-r`. Приоритет: флаг `--exclude` > `gone.exclude` > встроенное умолчание — каждый уровень целиком заменяет нижний |

```bash
git config --global gone.protect 'develop,release/*'
```

При запуске **без** `--yes` и не в TTY (через pipe) `git-gone` отказывается
удалять и выходит с кодом `1`. Передайте `--yes`, чтобы форсировать.

### Коды выхода

| Код | Значение |
|---|---|
| `0` | Успех — удалено, или удалять нечего, или режим отчёта (`--list`/`--dry-run`/`--json`) |
| `1` | Отмена в промпте, отказ без TTY, ветку не удалось удалить, при `-r` не удалось обновить репозиторий перед удалением, проинспектировать репозиторий или прочитать каталог, либо фатальная ошибка |

При `-r --json` репозиторий, который не удалось проинспектировать, отдаётся в поле
`error` **и** даёт код выхода `1`: документ печатается целиком, поэтому
`git gone -r --json > report.json` сохраняет полезную нагрузку, а `&&`-цепочки и
шаги CI останавливаются на неполном отчёте. Каталог, который не удалось прочитать,
даёт предупреждение в stderr и тот же код `1` — под ним могли быть репозитории.
Фатальная ошибка до формирования отчёта (не репозиторий, упавший `git fetch` в
однорепном режиме) даёт `1` и пустой stdout.

### JSON-вывод (`--json`)

Для CI / скриптов. Документ печатается **всегда**, в том числе когда gone-веток
нет — можно смело пайпить в `jq`.

**Форма JSON — публичный контракт по SemVer:** поля только добавляются в
minor-версиях, переименование/удаление — только в major. На это можно
завязывать CI. `skipped` несёт имена веток, которые не удалось распарсить
(не-UTF-8/TAB) — они доходят до машинного потребителя, а не только до stderr.
Защищённые ветки в `gone` не попадают вовсе.

Передайте `--include-reasons`, чтобы добавить массив `reasons`, не меняя
существующие поля. Каждый элемент содержит ветку, upstream-ref, который не
разрешился, и число коммитов, уникальных для ветки (`null`, если best-effort
подсчёт не удался):

```json
{"gone": ["feature-x"], "skipped": [], "reasons": [{"branch": "feature-x", "upstream": "refs/remotes/origin/feature-x", "unmerged_commits": 2}]}
```

Один репозиторий:

```json
{"gone": ["feature-x", "refactor/auth"], "skipped": []}
```

Multi-repo (`-r --json`) — `error` равен `null` для здорового репозитория и
содержит сообщение об ошибке для того, который не удалось проинспектировать
(такой репо никогда не выдаётся за чистый). `fetch_error` равен `null`, если
`git fetch --prune` прошёл (или был пропущен через `--no-fetch`); если там
сообщение — детекция всё же выполнилась, но на возможно устаревших
tracking-ссылках: `"gone": []` рядом с `fetch_error` — это *устаревший*
результат, а не подтверждённо чистый. В report-режиме сам `fetch_error` не
меняет код выхода, но при destructive `-r` этот репозиторий исключается из
удаления:

```json
{
  "repositories": [
    {"path": "clickhouse-toolkit", "gone": ["chore/x", "feat/y"], "skipped": [], "error": null, "fetch_error": null},
    {"path": "specification", "gone": [], "skipped": [], "error": null, "fetch_error": "`git fetch --prune` exited with status 128 in …"}
  ],
  "total_gone": 2
}
```

## Как это работает

- **Сначала fetch:** если не передан `--no-fetch`, перед детекцией выполняется
  `git fetch --prune` — без него ветка, удалённая на remote в другом месте,
  всё ещё имеет локальный tracking-ref и не будет считаться gone. При `-r`
  неудачный fetch фиксируется в JSON-поле `fetch_error`, а отчёты могут
  показать устаревшие кандидаты. Но удаление этот репозиторий пропускает и
  завершается с кодом `1`.
- **Безопасный режим:** `--safe` вызывает `git branch -d` и сохраняет ветку,
  которую Git не считает смерженной. По умолчанию остаётся `git branch -D`, так
  как gone-ветку уже нельзя смержить в удалённый upstream.
- **Fetch при `-r` параллельный** (`-j`, по умолчанию число CPU с потолком 8) —
  фаза fetch упирается в сеть и доминирует по времени. Прогресс
  (`[12/58] pkg-a`) показывается, когда stderr — терминал. Детекция локальна и
  последовательна, поэтому порядок отчёта всегда детерминирован.
- **Один репо:** `git for-each-ref` перечисляет локальные ветки с upstream;
  затем все upstream резолвятся одним вызовом `git cat-file --batch-check` —
  upstream, не разрешающийся в коммит, считается gone. Без матчинга строки
  `[gone]`, без зависимости от локали, и два процесса `git` на репозиторий
  независимо от числа веток.
- **Multi-repo:** рекурсивно обходит дерево каталогов, считая любой каталог с
  `.git` репозиторием. Meta-репо, который сам оборачивает per-package репо
  (монорепо с независимыми git-репо пакетов), обходится внутрь, а не
  считается leaf. Dot-каталоги и список по умолчанию пропускаются. Git-метаданные
  (включая `commondir`) обязаны резолвиться внутри scan root; gitfile или symlink,
  выходящий наружу, объявляется неуспешным scan и не используется.
- Все вызовы git идут через `std::process::Command` — без крейта `git2`/`gix`,
  без linkage libgit2. Один самодостаточный бинарь (~800 KB) с двумя
  зависимостями (`clap`, `anyhow`), использующий ваш собственный `git`,
  его конфиг и креды.

### Замечания

- Ветка, вычекаученная в **любом** worktree репозитория, никогда не является
  кандидатом: опрашивается `git worktree list --porcelain`, а не только текущий
  `HEAD` — такая ветка не попадает ни в отчёт, ни в попытку удаления.
- При удалении печатается короткий SHA (`Deleted branch: feature-x (was
  4f2a1c9)`): `git branch -D` — форсированное удаление, и именно SHA позволяет
  восстановиться через `git reflog` / `git branch <name> <sha>` — после любого
  прогона с удалениями печатается restore-подсказка.
- Листинг помечает ветки, чьи коммиты недостижимы из других ref —
  `feature-x (2 unmerged commits)` — решение об удалении принимается осознанно.
  Счётчик best-effort: если его не удалось посчитать, суффикс не показывается.
- Ветки, совпавшие с `gone.protect` / `--protect`, убираются из кандидатов с
  объявлением (`Protected branches skipped: develop`) — никогда молча.
- Имена веток с TAB или с не-UTF-8 байтами невозможно передать обратно в Git,
  поэтому они **пропускаются с предупреждением** — не попадают в gone и не
  удаляются. Тихо считать их gone было бы хуже: имя с потерями не резолвится ни в
  один ref, что выглядит ровно как «upstream удалён».
- Ref, имя которого начинается с `-` (создаётся через `git update-ref`, но не
  через `git branch`), обрабатывается: имя передаётся после `--`.

## Безопасность

- **`-r` запускает `git` в каждом найденном каталоге, а значит исполняет *их*
  конфиг.** Git выполняет настройки уровня репозитория (например
  `core.sshCommand`) во время `git fetch`; чужой репозиторий — это исполняемый
  контент. Не запускайте `git gone -r` над деревом с недоверенными клонами — либо
  передавайте `--no-fetch`, что ограничивает прогон осмотром локальных ссылок.
  (`safe.directory` защищает только от репозиториев, принадлежащих *другому*
  пользователю, и не помогает с недоверенным репозиторием, который вы склонировали
  сами.)
- **Метаданные рекурсивно найденного репозитория ограничены scan root.** Вложенный
  `.git` gitfile, symlink или `commondir`, резолвящийся за пределами запрошенного
  дерева, отклоняется и делает scan неуспешным: он не может перенаправить удаление
  в несвязанный репозиторий. Linked worktree с Git-метаданными вне scan root нужно
  обрабатывать из дерева-владельца. Для доверенного layout, которому это нужно,
  есть явный opt-in `--allow-external-git-dir`.
- **Неудачный fetch блокирует удаление в этом репозитории.** `--json`, `--list` и
  `--dry-run` могут показать устаревшие tracking-ref с `fetch_error`; обычный и
  `--yes` рекурсивные прогоны такой репозиторий никогда не удаляют и завершаются
  с кодом `1`.
- **Запросы кредов отключены при `-r`** (`GIT_TERMINAL_PROMPT=0`): один
  репозиторий с приватным remote иначе подвесил бы весь пакетный прогон на
  запросе пароля. В однорепном режиме промпты остаются включёнными. Ограничение:
  это покрывает промпты самого Git (HTTP-креды); `ssh` всё ещё может спросить
  passphrase ключа или подтверждение host key. Для полностью автономного прогона
  используйте `ssh-agent` либо `--no-fetch`, чтобы вовсе не фетчить.
- **Удаление форсированное** (`git branch -D`) — так задумано: remote уже удалён,
  а `-d` отказался бы удалять незамердженные ветки, которые уже некуда мерджить.
  Печатаемый `(was <sha>)` — ручка для восстановления; кончики веток также
  остаются в reflog до его истечения.
- **Ничего не проходит через shell.** Каждый вызов git — это
  `std::process::Command` с вектором аргументов, имена веток передаются после `--`.
- **Загрузки установщиков проверяются по контрольной сумме.** И `install.sh`, и
  `install.ps1` качают опубликованный `<asset>.sha256` и отказываются ставить при
  несовпадении — конвейер `curl … | sh` падает, а не выполняет подменённое.
- **Никакого `unsafe`**: крейт помечен `#![forbid(unsafe_code)]`.

## Разработка

```bash
cargo fmt
cargo clippy --all-targets --locked -- -D warnings
cargo test --all --locked
cargo run -- --list
cargo run -- -r --dry-run
```

Требуется Rust 1.85+ (edition 2024; см. `rust-version` в `Cargo.toml`).

Раскладка: `cli.rs` (флаги), `git.rs` (все вызовы `git` и парсер детекции),
`scan.rs` (обход каталогов), `report.rs` (результат по репо и агрегаты),
`json.rs` (сборка документов), `run.rs` (два режима), `main.rs` (диспетчер).
Unit-тесты лежат рядом с кодом, который покрывают; `tests/integration.rs`
